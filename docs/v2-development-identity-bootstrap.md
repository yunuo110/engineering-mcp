# V2 development identity bootstrap

**DEVELOPMENT-ONLY IDENTITY PROVISIONING — NOT A PRODUCTION CREDENTIAL DESIGN**

The isolated V2 test harness creates disposable local standard-user identities for Keeper and Worker. The operator/test harness generates a fresh random password for each identity in each test round, records only the process SID and group/privilege evidence, and deletes the identities after the round. Production accounts, production ledger, B3, real model processes, and real repositories are outside this mechanism.

The native `execution-bootstrap.exe` (`engineering-execution-bootstrap/2`) runs with the Core test token. It creates an unnamed Job, starts the trusted Runner suspended with that token, assigns and verifies Job membership and policy, then starts `execution-keeper.exe` under the disposable Keeper identity with `CreateProcessWithLogonW` and `dwLogonFlags = 0` (no persistent test-user profile load). Its only credential input is a bounded binary frame on an anonymous standard-input pipe established by the operator/test harness through the trusted Controller. The frame contains four length-prefixed fields: Keeper UTF-8 local username, Keeper NUL-terminated UTF-16 password, Worker UTF-8 local username, Worker NUL-terminated UTF-16 password. Each length is a four-byte little-endian integer. Usernames are limited to 256 bytes and passwords to 1024 bytes including the terminator. Credentials are never executable arguments or environment variables. The helper pins the Keeper password byte buffer for the Win32 call, clears it immediately afterward, closes the input channel on success and failure, and never serializes it to the ledger, witness, receipt, manifest, or log. The supplying harness clears its source buffer after the pipe write completes. A missing, malformed, or partial channel fails the launch without fallback; partially read buffers are cleared by the read operation itself.

The helper duplicates `JOB_OBJECT_QUERY` and `PROCESS_QUERY_LIMITED_INFORMATION` handles into the Keeper process, using private standard pipes to deliver the handle values and receive `SEALED` / `RESUMED` publication acknowledgements. Keeper publishes `runtime.sealed.json` atomically before `SEALED`; only then does the helper resume Runner once. Keeper publishes `runtime.resumed.json` before `RESUMED`. Handoff commits only after that acknowledgement. Every earlier failure terminates and waits for the exact Keeper and Runner process handles, then closes them.

Runner inherits only its dedicated Worker-identity stdin pipe and null output handle through `PROC_THREAD_ATTRIBUTE_HANDLE_LIST`. Bootstrap separately duplicates a non-inheritable Job assign/query handle into the trusted Runner. Its stdin frame is the eight-byte little-endian handle value followed by the two Worker credential fields. Runner closes this channel after one read and consumes its in-memory credential on one adapter launch. Keeper retains only observation authority; Runner alone owns claim/report operations.

All default Generic CLI and Codex/Luna adapter launches use the protected `execution-worker.exe` (`engineering-execution-worker/1`). This Core-token helper receives the one-time Worker credential and a bounded launch description over stdin and forwards only the subsequent task protocol to Harness stdin. Node launches this helper with `boundedControlEnvironment()`, explicitly blanking libuv's built-in environment fallbacks. The native environment block explicitly sets `HOMEDRIVE=C:`, `HOMEPATH=\`, and `SystemRoot=C:\Windows`; these are fixed development values, not observed account-profile evidence. The home variables prevent the logon API's documented insertion of omitted values. No live model credentials are provisioned by this milestone. The helper creates Harness suspended with `CreateProcessWithLogonW`, verifies its actual user SID, rejects Core/Keeper/operator/SYSTEM and any Administrators group (including deny-only membership), requires Medium integrity and no elevation, assigns it to the same unnamed Job, and only then resumes it. Administrators membership is read from raw native `TokenGroups`; `.NET Framework`'s `WindowsIdentity.Groups` filters out deny-only entries and is not used for this check. Only the three new task stdin/stdout/stderr pipe handles are inheritable at creation; secret, token, Runner and Job handles are not. An absent identity source refuses execution; standard package initialization does not imply Worker execution has been provisioned.

Native secret stdin uses an owning `SafeFileHandle`, detached from the standard-handle table, and a one-byte `FileStream` buffer. Closing it closes the OS handle; `Console.OpenStandardInput().Close()` is not used. Worker relay shutdown marks both exact input handles closed, cancels outstanding reads/writes using `CancelIoEx` while retaining handle references against reuse, and waits at most one second for its input pump. Cleanup refuses a timed-out drain. Both logon launch sites reject command lines longer than the API's 1024-character bound before calling it. Unit environment-block assertions do not establish the observed environment of a real alternate-identity Harness.

The no-account native tests prove partial-read clearing, role comparison rejection, raw Administrators SID rejection with enabled/disabled/deny-only attributes, and exact suspended-child termination/wait. Those tests do not establish successful alternate-identity execution. Actual restricted Worker acceptance and public execution E2E require the separately authorized disposable identity host; real Codex/Grok and production remain HOLD.

The launch path must use a protected, version-bound trusted runtime binding and verify every control artifact before spawning this helper. A secret channel cannot substitute for that preflight. Failure after dispatch reservation leaves the reservation authoritative unless the implementation proves no child process was created; it never starts an unmanaged Keeper or Runner as fallback.

Test cleanup must verify that all fixture processes have exited and delete the disposable accounts and any disposable user profiles. Isolated evidence roots remain protected for inspection until an explicit cleanup decision. Cleanup failures are HOLD. Test evidence may contain account role names, SIDs, integrity levels, ACLs, process IDs, and error classes; it must not contain passwords. The test harness must separately inspect process command lines, process environments, witness/receipt/ledger bytes, and ordinary logs for credential absence.

**Production identity provisioning remains UNRESOLVED / HOLD:** Keeper and Worker account lifecycle, credential storage and rotation, service-account policy, and the final alternate-token primitive (`CreateProcessAsUser` or another design) require a separate OWNER decision. Passing this development experiment does not authorize a production credential design or a Phase 2C execution E2E.
